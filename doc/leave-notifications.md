# Leave request mail notifications

Submission, cancellation request, and completed approval/rejection of either request insert one outbox job per audit event in the same transaction. Failed transactions leave neither request nor notification. Existing historical requests are not backfilled. Decision results go only to the employee, using their current active account mailbox. Employee withdrawal sends no email. Each result is rendered from its immutable decision event (including the decision date and approval comment), so later cancellation does not rewrite the earlier result. Duplicate decisions are rejected before another mail is queued. Cancellation approval explicitly states the leave is cancelled; rejection explicitly states the leave remains approved. No new Admin popup is introduced.

The sole notification worker reads the current direct manager at dispatch, requires an active, non-deleted, non-archived account with review rights and a valid mailbox, and never emails the applicant as their own reviewer. No available recipient means `no_recipient`: keep the ordinary Admin pending task, and retry recipient resolution hourly without broadcasting to administrators. Review reminders already handled/withdrawn/archived become obsolete before send. Historical decision mails retain their own result and decision timestamp even if a subsequent action occurs.

Mail contains the employee display name and requested dates/half-days, but no applicant free-text note, password, social security number, attachment or approval token. Result mail includes the approval comment from its decision audit event, escaped in HTML. Its HTTPS button opens `?leave=<request id>`. The browser preserves this query during login and opens exact leave details after authentication; the server still checks access and every approval remains explicit.

`leave_notification_outbox` stores event/request IDs, kind, dispatch state, attempts, recipient account ID and timestamps. Only pending/retry/no_recipient jobs are claimable under a transaction lock. Known pre-send connection failures retry up to five attempts. An uncertain SMTP DATA result or abandoned claim is not automatically resent, avoiding silent duplicate sends. SMTP acceptance does not establish inbox delivery. Failed/uncertain jobs require operator inspection; a notification status/resend UI is not included yet. Do not manually resend an uncertain job without checking delivery.

Runtime: `backend/leave_notifications.py`, hooked by `main.py` into `leave_requests.py`. `PRESENCE_LEAVE_NOTIFICATION_WORKER=1` enables the worker using existing SMTP/TLS settings and the public HTTPS `PRESENCE_APP_URL`. Set it to 0 on candidate services and local environments; the local entry forces 0. The local queue can be inspected without real sending. Do not deploy a candidate with this worker enabled against live requests.

Tests: `test_leave_notifications.py`, real MySQL temporary-table test in `test_responsable_workflow_mysql.py`, and frontend `leaveLink.test.mjs`. All delivery tests use mocks; no real emails are sent.
